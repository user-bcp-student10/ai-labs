# HU-01: Token de autenticación verificable

## Origen
- **H-AUTH-03 — Token Base64 con secreto embebido y sin firma verificable** (Pendiente). Evidencia: `auth/src/main/java/com/bcp/workshop/auth/LegacyTokenUtil.java:8,12-15`.
- **H-AUTH-05 — Secreto hardcodeado y CORS con origen permisivo** (Pendiente; alcance de esta HU limitado a la exposición del secreto mediante el token legacy). Evidencia: `auth/src/main/resources/application.properties:5,9`; `auth/src/test/java/com/bcp/workshop/auth/AuthResourceTest.java:97-106`.

## Contexto
El token legacy concatena el secreto con su contenido y lo codifica con Base64. Base64 no aporta integridad ni confidencialidad, por lo que el contenido y el secreto pueden recuperarse y los cambios no se detectan. Aunque el secreto ya está externalizado, el formato legacy todavía lo expone. La matriz registra que `POST /auth/login` responde con `token` y `expiresIn` al autenticar correctamente.

## Ajustes necesarios
- Reemplazar la construcción Base64 legacy por un mecanismo de token con firma verificable, sin exponer el secreto en el token.
- Definir el formato y el mecanismo de firma y verificación; la matriz no prescribe una tecnología o algoritmo.
- Conservar el contrato observado de `POST /auth/login`, incluidos los campos `token` y `expiresIn` en una autenticación exitosa.

## Criterios de aceptacion
- Una prueba unitaria verifica que el token emitido tiene una firma válida para el mecanismo de verificación implementado.
- Una prueba unitaria altera el token emitido y verifica que la validación rechaza la alteración.
- Una prueba con configuración aislada verifica que el secreto configurado no puede recuperarse del token emitido; no se usan secretos reales.
- Una prueba de `POST /auth/login` verifica que una autenticación exitosa conserva la respuesta HTTP 200 y los campos `token` y `expiresIn`.

## Evidencia esperada
- Pruebas unitarias de emisión y verificación, incluida la detección de alteraciones y la no exposición del secreto, con sus resultados.
- Resultado de la prueba de contrato de `POST /auth/login`.
- Cambio revisable del mecanismo de token y confirmación de que no se añadieron tokens, secretos ni credenciales reales.
